# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. The ordinary `pnpm run build` produces the static GUI in `dist/client`; run `pnpm run test:evidence` for its evidence/adapter checks. Keep the local `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Sites packaging uses that local hosting configuration: run `pnpm run build:sites` and `pnpm run test:sites`; the Sites build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Prototype-specific decisions

- Default to English for the ENG5105 presentation GUI, with a top-bar language menu that switches the complete interface between English and Simplified Chinese. Every new user-facing string must be provided in both languages.
- The dark industrial dashboard mock in `design-reference/selected-dashboard-concept.png` is **no longer the visual source of truth**. On 2026-08-21 the user rejected that look as generic, and the interface was given its own visual system. Keep the mock only as a record of the original content and layout intent.
- Visual system, in force from 2026-08-21 with the user's 2026-09-20 surface decision:
  - Glass replaces the matte surface treatment, with a fixed CSS-gradient backdrop behind the shell. Keep the warm graphite ground and bone / oat / amber / rust palette: bone (the filament under light) is the primary value colour, and amber and rust are the only signal colours. **There is no green anywhere** — a healthy run is shown by the frame heartbeat running and nothing being flagged, not by an all-clear light. Do not reintroduce a green "OK" state.
  - The backdrop's brightest point must not exceed `#24271f`. Panel tint is `rgba(25, 28, 24, .55)` and the sidebar and topbar are `.6`; against a backdrop at that ceiling the weakest text colour, `--oat-dim`, still holds WCAG AA at 5.55:1. Glass transparency is bounded by what sits behind the surface, not by taste: panels and the desktop chrome only ever sit on the backdrop, so they can be this open. Below 760px the sidebar becomes a sticky bar with the page — including the near-white evidence frame — scrolling under it, and there anything below `.9` drops `--oat-dim` under AA, so it is pinned at `.94`. Re-derive these numbers before changing a tint or the backdrop.
  - Archivo Variable (width axis 62–125) for prose and furniture, IBM Plex Mono for values. The rule is load-bearing: **if a machine produced the value it is mono; if a person wrote it, it is Archivo.** Keep new fields on the right side of that line.
  - Glass has three tiers. Tier A uses at most three real `LiquidGlass` instances: the language dropdown, the sample-capture camera dialog, and one wrapper around the whole KPI strip. Each instance adds its own SVG filter graph and `mousemove` listener, so keep displacement out of dense mono data. Tier B uses CSS glass without displacement or pointer tracking for panels, the sidebar and the topbar, with an opaque fallback where backdrop filtering is unsupported. Tier C keeps the inspection frame, its image and table body rows opaque.
  - The inspection picture is never cropped, never letterboxed, and never has chrome on top of it. `.camera-stage__frame` takes its aspect ratio from the decoded frame, and every readout lives in the rails above and below. Glass may treat the panel frame and rails, but never cover the opaque inspection frame or its image.
  - Motion budget is the nav indicator sliding, a view assembling once on change, the press feedback on a copied value, the heartbeat, and restrained Tier A pointer refraction. Anything beyond that needs a reason. All of it respects `prefers-reduced-motion`; the local glass wrapper observes media-query changes and uses `elasticity={0}` without `mouseContainer` while reduced motion is requested.
  - Measured parameter rows are click-to-copy, with a fallback for the plain-http case where `navigator.clipboard` is absent.
- Fields that are not measured get a designed row rather than being dropped: size and web position appear in the candidate panel with a struck rule where the reading would be. This is driven by `snapshot.physicalMeasurementsAvailable`, so it disappears on its own once calibration exists. Do not replace it with a hidden field or a footnote.
- The GUI defaults to the resident camera/inspection service and also supports explicitly selected offline simulation and archived integration evidence. Describe the active source and evidence level from its data contract; the existence of a GUI control does not establish hardware integration.
- The selected camera is Plan A's ALC-IMX258 USB/UVC module. The resident service supports it alongside Plan B's ESP32S3/OV3660 MJPEG adapter. Derive active camera labels from source metadata, preserve historical Plan B replay identity, and retain the existing shared inspection/API/database/GUI contract. USB software tests do not establish delivered-camera performance.
- Do not couple React components directly to camera, STM32, encoder, alarm, or database implementations; consume the unified inspection data-source contract.
- Offer Sample capture / 样本采集 in the primary GUI navigation, with a return link to inspection. Keep week numbers out of navigation. Preserve the accepted layout, direct angle/lighting capture, bilingual copy, evidence, calibration and output states.
- The Week 5/6 public demo must not show controls that imply unconnected hardware actions. Keep alarms, safety state, and adapter configuration read-only until their real backend interfaces are integrated and validated.
- Keep navigation focused on Live Inspection, Candidate Records, System Health and Sample capture. Use task-oriented names. Batch analytics and writable hardware settings require their real data and interfaces.
- Default the GUI to the camera service at http://127.0.0.1:8765. Derive camera identity from the service response. A disconnected camera or unavailable/stale service leaves the live picture empty and offers retry; never substitute synthetic evidence or an old frame. Offline replay requires an explicit mode and retains its original source identity.
- Selecting a recorded candidate pins that record's saved evidence image in the inspection viewer. The automatic fault timeline may continue internally, but it must not replace the selected image until the user returns to fault replay.
- Live Week 4 evidence must be described as a captured OV3660 integration snapshot, not a continuous stream. Scene candidates from the ceiling/glare test are unvalidated and must never be presented as rPLA defects or actuator grades. Because the current live run retains only the latest annotated image, live candidate rows are read-only and must not imply frame-specific image evidence.
- The final-project GUI groups consecutive, spatially overlapping frame-level candidates into one displayed candidate event. Raw frame records remain available for CSV/database traceability, while the dashboard and records page show event-level results and avoid validation-status notes.
- Local service mode uses the resident Python inspection service as the sole acquisition client for the selected USB or ESP32 source. The GUI receives the shared processed stream from the service and live state/candidate updates over WebSocket.
- Live candidate events may be deleted from either the dashboard or records page. Deleting one collapsed event must remove every linked raw detection from both the resident service and SQLite after explicit confirmation.
- Preserve the current laptop density, but automatically enlarge the full interface at 2K and 4K desktop breakpoints so small industrial-dashboard text stays legible on a 27-inch external display.
- Keep the live operator view focused on connection, pipeline rate, candidate events, and post-decode GUI latency. Do not promote cumulative frame counts, inspection-frame counts, recovery counters, buffer policy, or skipped-frame counters as primary KPIs; keep secondary engineering diagnostics in the System Health technical-details disclosure and do not repeat a health-card strip on the live page.
- Give the inspection image the main column and its candidate the adjacent column; show saved candidates across the next row. Keep simulated fault timelines in System Health. Preserve readable density and aspect ratio across laptop and external-display sizes.
- Explicit Plan A replay and new offline sample sessions use native 3840x2160 synthetic images. Generate scene geometry, pixel noise, ROI and candidate records at the configured size. Keep the small reference fixtures for fast regression tests, and preserve archived captures at their original dimensions.
- Display actual decoded image dimensions separately from a requested camera mode, including when they match. Requested values and synthetic evidence do not establish camera performance. Never combine differing source/resolution configurations in one sample session.
- Sample capture selects one angle and one lighting mode, then captures that view directly. Bright and dark field are separate views; retake confirmation and success feedback identify that exact view. Missing coverage cells can prepare the corresponding capture.
- Each sample session has an individually confirmed delete action that names the session and removes its images, candidates and history; other sessions remain intact. Do not delete user archives during verification.
- Sample capture reads health, preview and captures from the same resident camera service. Camera capture is enabled only when its response grants connected and capture_available; poll health while mounted and revoke capture on failure. Device/mode/ROI settings live in service startup configuration; do not request browser camera permission.
- Physical lighting is manual and recorded as operator_declared. The operator sets angle and illumination then captures directly; do not add repeated angle/lighting confirmations or imply sensor-confirmed READY/OFF. Keep retake and destructive deletion confirmations. Saved image selection stays pinned independently of camera preview.
- Label area-derived values as ranking scores, and expose a saved record's image from Candidate Records. Keep prototype grades in traceable data exports; they are not physical quality decisions or rejection commands.
- The Plan B resident service uses named resolution profiles with normalized ROI scaling. Keep SVGA 800×600 as the fixed live default selected on 2026-08-11; do not continue resolution-selection trials. VGA remains a manual fallback only.
